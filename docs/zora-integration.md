# The visualizer as ZORA's spoiler view

Status: research and design only (2026-10-05). No code has changed in either
repo. Checked against z1r-visualizer at `1822838` and ZORA 0.2.0 (zora-ng's
wheel `zora-0.2.0`).

Sources: this repo; zora-ng's public interface only (`zora/api.py`, `docs/`,
`web/`). ROMs were generated by calling `zora.api.generate_rom` from a scratch
folder outside both repos; nothing was written in zora-ng.

**Update (2026-10-06):** the hand-off contract is defined and built: the seed format
(`docs/seed-format.md`, with its JSON Schema), which the visualizer's ROM reader also produces,
and the "View in Visualizer" handshake (section 5 there). This page is the earlier research.

## Owner decisions (2026-10-06)

1. "Encode level data" is plain ON/OFF; ZORA will refuse "?" on it. A spoiler
   is offered only when it is off. Section 4.1's "?" problem no longer arises.
2. The spoiler **should** show how the flags' "?" settings resolved. The ROM
   can't tell, so ZORA passes those values in, along with progressive
   meaning, one-time wares and who says which hint. This favours D or E with
   facts from ZORA, or C.
3. Licence undecided: do not plan on copying visualizer code into ZORA yet,
   but keep the design open for it.
4. Visualizer fixes approved and done: W1 (magical sword), W2 (progressive
   lines, keyed on ZORA's byte), W3 (all 41/45 texts, plus a "Hint Texts"
   view), W4 (recorder text) and W5 (the decoder-JSR marker; the heuristic
   stays as well). W6 (wording) was done with W5's error message. Tests are
   in `data_extractor_test.py` (`ZoraRomTest`).
5. Next: a static, GitHub Pages visualizer (docs/static-hosting.md).

**Hard rule, applies to every option below.** A seed made with "Encode level
data" must stay unreadable. Any spoiler view, button, export or link applies to
unencoded seeds only, and must not reveal whether a "?" resolved to encoded
(section 4.1).

## 1. Does the visualizer read ZORA's unencoded ROMs today?

### 1.1 What was tested

- The Consternation preset without level encoding (`8hq4BeR1JXo89BJ2!TFpTP02u8UJ3A`)
  with these ZORA flag strings: none, `1.D` (Randomize Magical Sword, cap 12),
  `1.2` (Randomize Letter), `1.F` (both), `2.m` (Shop Items in the Item Pool).
- Progressive Items (`2.O`, and `2.19` with the shop pool) needs B09 (extra
  candles) off, so it ran on the same preset with B09 off
  (`8hq4BeR1JXo7yjOOHjbxryVQW!UJ3A`).
- Each case had 3 seeds read in detail. On top of that, 300 seeds were scanned
  automatically for parse failures and for where the magical sword landed.
- One control seed used the Consternation preset with encoding on, plus the
  two ZORA playtest ROMs already in `testdata/`.

### 1.2 What it gets right

- **Parsing.** 200 of 200 unencoded seeds parse, across four ZORA flag
  strings, with no `ERROR CODE` room types, enemies or items. Every level
  passes `_ValidateLevelData`. ZORA writes 2 (south) as every level's
  entrance byte, which is what the visualizer expects (`is_z1r` is true).
- **Encoded seeds are refused.** Both encoded ROMs fail with
  `GarbledLevelDataError`, and the app then hides the maps and the item
  summary.
- **The "$0E" nothing code is mostly right already.** Since `0e987b6` the
  visualizer reads the nothing code from the engine's compare at file
  `0x1785F`, where ZORA writes `$0E`. Empty rooms show nothing. Ganon's room
  still shows the Triforce of Power: it did in 100 of 100 sword seeds.
- **Caves, shops and prices** are read correctly, including Shop Items in the
  Item Pool. Shops then sell major items, such as a Magical Key for 59, a Wand
  for 185 or a Heart Container for 37. The letter cave and magical-sword cave
  show whatever item landed there. The app already treats `$03` in a cave as
  the Magical Sword.
- **Randomize Letter**: the letter shows correctly wherever it lands (a level
  room, Armos, ...).
- **Requirements**: the white-sword and magical-sword hearts, the level-9
  triforce count and the door-repair charge all read correctly.
- **Hint texts**: the first 38 texts decode cleanly, ZORA's own hints
  included ("THE GLEEOK HOLDS THE RED RING", "A SWORD UPGRADE NEEDS THE
  LADDER", the magical-sword cave's "MASTER USING IT AND YOU CAN HAVE THE
  HEART CONTAINER"). Note that only `cli.py` prints texts; the app shows
  none.

Not verified: the map walk itself against ZORA's ground truth (doors,
staircases, room positions). That would need ZORA's internal model, which is
outside the public interface. Room counts look plausible: 13 to 60 rooms per
level, every level at most 64. ZORA's extra "exit rooms" (fp-entr-02, the
level-info byte `+$23`) are not shown, and nothing checked whether they
matter for a spoiler.

Not ZORA-specific, but worth knowing: three tests in `data_extractor_test.py`
fail because their ROMs (`testdata/z1.nes` and two Z1R ROMs) are not in
`testdata/`. The two ZORA playtest tests pass.

Also readable, and nice to show: the seed code. The four item IDs at file
`0x0AFB0` (`ZORA_B2_CodeIcons`) match the code on ZORA's page. For example,
seed 1 has `1D 0F 16 0F`: Boomerang, Five Rupees, Compass, Five Rupees.
Showing it lets a player confirm they loaded the right ROM.

## 2. The integration options

Facts that shape every option:

- **The visualizer** is a Streamlit app (server-side Python, Bokeh and
  pandas). It is hosted on Streamlit Community Cloud, and an uploaded ROM
  goes to that server. Its parsing core (`data_extractor.py`, `rom_reader.py`,
  `constants.py`, about 38 KB) uses only the standard library: `io`, `math`,
  `typing`.
- **ZORA's beta** is one HTML file opened from disk. It runs Python in
  Pyodide in a Web Worker and fetches only Pyodide's five files from
  jsDelivr. Its page promises "Your ROM is read in this page only and is
  never uploaded". Testers are asked not to share the file. The generated ROM
  is already in the page as bytes (`result.bytes` in `onGenerate`).
- **Licences.** ZORA is "All rights reserved, licence to be announced". The
  visualizer has **no licence file**. That means all rights reserved by
  default, even though the GitHub repo is public. Its commits are all by the
  owner (tetraly, two addresses, and "Tetra"), plus one commit made with
  Claude for the owner. So the owner can move code between the two freely.
  The question is only what notice it carries afterwards (section 5).
  Third-party code matters only if Bokeh (BSD-3), pandas (BSD-3) or Streamlit
  (Apache-2.0) would ship inside ZORA. The parsing core uses none of them.

### Option A: a plain link (simplest)

After a seed is generated, ZORA shows "View the spoiler in Z1R Visualizer"
next to Download, for unencoded seeds only. The player downloads the ROM and
drops it into the hosted visualizer.

| | |
|---|---|
| ZORA effort | About 10 lines in `zora-web.js`. |
| Visualizer effort | W1-W6 (about a day), so the spoiler is not wrong. |
| Maintenance | Two codebases, as today. The visualizer follows ZORA's byte layout by hand (W2, W3). |
| Licensing | Nothing moves. |
| Single-file beta | Poor. It needs the network and a third-party server. It uploads the generated ROM, which holds Nintendo's code and a confidential beta's output, to Streamlit Cloud, against the page's "never uploaded" spirit. It also points beta testers at a public site. |
| Encoding | Safe: the visualizer refuses encoded ROMs (W5 makes that certain). |

### Option B: "Open in Visualizer" with an automatic handoff

- **B1. The ROM in a URL.** Rejected. 128 KB of ROM becomes about 175 KB of
  base64, beyond what servers accept in a URL. It also puts the ROM in
  server logs and browser history. Streamlit reads only the query string,
  never the `#fragment`, so the data would reach the server either way.
- **B2. Same-browser handoff** (`window.open` plus `postMessage`, or
  `BroadcastChannel`). The beta's origin is `file://` (`null`) and the
  visualizer is on `streamlit.app`. Only `postMessage` crosses that boundary.
  Streamlit's Python cannot receive it without a custom JavaScript component,
  and the ROM still ends up on the server. High effort for little over A.
- **B3. A small spoiler payload in the URL** (compressed JSON, a few KB). Only
  possible once option C exists. It would still send that payload to a
  server.

Verdict: none of B is worth building while the visualizer is a server app.

### Option C: a spoiler export file from ZORA

ZORA writes a small JSON file from its own model (`GameWorld` and the
`ExtraPoolItems` it already stages). It holds every place and its item, with
progressive items as their line and one-time wares marked; shop prices; which
person or cave says which hint; the requirements; and the seed, flags, ZORA
flags and seed code. The visualizer loads it next to the ROM and lets it
override what it cannot know.

| | |
|---|---|
| ZORA effort | Medium: a versioned format, a writer, tests and a second Download button. zora-extras.md already notes that "ZORA has no spoiler output yet" (SI-JOIN-02), so this may be wanted anyway, for example for Archipelago, which ZORA means to ship in. |
| Visualizer effort | Medium: an optional second upload, and merging its facts into the tables and tooltips. |
| Maintenance | Two codebases, joined by one documented format instead of ZORA's byte layout. That is better than A: ZORA can move `$BE40` (it did in 0.2.0) without breaking the visualizer. |
| Licensing | Nothing moves. The format is data. |
| Single-file beta | Fine to produce: it is one more download. Viewing still means the hosted visualizer (A's problems). |
| Encoding | ZORA must **never** write the file for an encoded seed. That is easy to enforce at the writer and to test. |
| Extra risk | The file names the resolved "?" outcomes in plain words, more bluntly than maps do. That is the owner's call (section 5). |

### Option D: a spoiler tab inside ZORA's page, using the visualizer's parser

After an unencoded seed is generated, a "Spoiler" tab or panel (behind a
deliberate click) shows the levels, overworld caves and an item summary. The
worker runs the visualizer's parsing core on the generated bytes in Pyodide
and returns `DataExtractor.data`, `shop_data` and the requirements as JSON.
The page draws them as SVG. The ROM never leaves the page.

| | |
|---|---|
| ZORA effort | Medium. Add the parser to the wheel, or a second embedded wheel, and add a `spoiler` worker message. The SVG renderer is the bulk of the work, perhaps 300-500 lines of JS for the level grid, doors, walls, labels and caves, styled with ZORA's CSS. |
| Visualizer effort | Small: W1-W5, and maybe a `to_json()` on `DataExtractor` so both sides consume the same structure. |
| Maintenance | **One parser** if ZORA vendors a pinned copy and never edits it, with the visualizer repo as the source of truth and fixes going there first. **Two renderers** (Bokeh here, SVG in ZORA), unless the visualizer later adopts the same renderer. Practical traps: ZORA's wheel is built only from committed `zora/` (`git archive`, then `check_wheel.py`), and mypy runs strict over `zora/`. The visualizer's code is not strict-clean (for example, `GetRequirements -> int` returns a dict). So vendor it outside `zora/`, for example as its own small wheel inlined next to ZORA's, or clean its types first. |
| Licensing | Visualizer code would ship inside ZORA's beta, under ZORA's notice. Both are the owner's, so this works today. Section 5 asks what licence it carries later. No third-party code is involved, since Bokeh, pandas and Streamlit stay out. |
| Single-file beta | Good. It adds about 40 KB of Python (about 10 KB zlib) and the renderer. No new network fetch. Works offline. |
| Encoding | The worker must not run the parser at all unless the seed is unencoded (section 4.1), so no spoiler data exists even in the developer console. |
| Weakness | Still limited to what the ROM shows. W2 and W3 (progressive lines, who says which hint) need either the visualizer to read ZORA's patch bytes, or ZORA to hand over a few facts from its own result. The second is cheap here, because the worker has them. |

**Variants considered and rejected:**

- Running the whole Streamlit app in the page through stlite (Streamlit on
  Pyodide). It would need Streamlit, Bokeh and pandas, tens of MB from a CDN,
  which defeats the offline single file.
- An `<iframe>` of the hosted app. That is option A plus cross-origin
  problems.

### Option E: ZORA draws its own spoiler from its own model

ZORA already holds the truth: rooms, doors, staircases, every place's item,
progressive meaning, prices and the hint assignment. A renderer fed directly
from `GameWorld` needs no ROM parsing and cannot misread. The visualizer's
walk has needed several "phantom staircase" fixes over the years, which
shows parsing is the fragile part.

| | |
|---|---|
| ZORA effort | Highest: the same renderer as D, plus a model-to-view layer written fresh. |
| Visualizer effort | None. |
| Maintenance | One codebase. It changes with the model, so it is always correct. The visualizer stays for Z1R and for ROMs from elsewhere. |
| Licensing | Nothing moves. |
| Single-file beta | Good, same as D. |
| Encoding | Same gate as D. |
| Honest note | This does not use the visualizer. It is listed because it is the most correct end state, and the export of option C would come out of it almost for free. |

## 3. What each side needs, and the recommendation

### 3.1 Recommendation

1. **Now, in this repo only: fix W1, W3, W4, W5 and W6.** Each is small. They
   make the visualizer right for every ZORA seed people already drop into it,
   and W5 strengthens the encoding guarantee. W2 (progressive) is better left
   to step 2's facts from ZORA than to reading `$BE40` here, but a minimal
   "this ROM uses Progressive Items: sword, candle, arrow, ring and boomerang
   items are upgrades" banner, keyed on that byte, would cost little.
2. **For ZORA's page: option D**, a spoiler panel behind an explicit click,
   built from the visualizer's parser running in the worker. The worker adds
   the few facts the ROM cannot tell from its own result (progressive on, the
   one-time wares, the hint assignment). This fits the single-file offline
   beta, keeps the ROM in the page, reuses the part of the visualizer that is
   costly to get right (the walk), and needs no new network.
3. **Skip A and B for the beta.** A plain link is fine later for a public,
   hosted ZORA, once the owner is happy to point testers at streamlit.app.
4. **Option C (export) only on demand**, for example if Archipelago or racers'
   tools want a spoiler. If ZORA ever builds E, C falls out of it.

### 3.2 What D needs, side by side

| Visualizer (this repo) | ZORA (zora-ng; owner's work, not done here) |
|---|---|
| W1, W3-W5 fixes; tests on generated ZORA ROMs in `testdata/` | A `spoiler` worker message: runs the parser on `result.bytes` only for unencoded seeds (section 4.1) and returns JSON |
| `DataExtractor.to_json()`: a plain, documented dict (levels, rooms, doors, walls, stairs, overworld caves, shop data, requirements, quotes) | Ship the parser: a pinned copy outside `zora/`, or a second small wheel inlined by `build_site.py --single-file`; the private-strings grep stays as it is |
| A tagged release or commit for ZORA to pin | An SVG renderer and a "Show spoiler" control in the generate result, after the Download button |
| Optionally: stdlib-only and strict-typed core, so it can live under ZORA's mypy and ruff | Overlay facts from ZORA's own result: progressive lines, one-time wares, the hint assignment |

### 3.3 Why not have the visualizer read more ZORA internals?

W2 and W3 can both be done by reading bytes that rom-map.md documents. But
ZORA's layout moves between versions: the extended hint area's end moved from
`$BEAD` to `$BE40` in 0.2.0. Every such read must then follow ZORA's
changelog. Keep the visualizer's ZORA-specific reads to stable facts (the
nothing code, the pointer count, the encoding marker) and get the rest from
ZORA as data.

## 4. Rules any option must keep

### 4.1 Encoding and "?"

ZORA's page never shows what a "?" resolved to, including "Encode level data"
(`onGenerate`: "the page never shows what a '?' field resolved to"). If the
spoiler control appeared only for seeds that came out unencoded, its presence
would reveal how a "?" on encoding resolved. Proposed rule:

- Offer a spoiler only when the player explicitly set "Encode level data" to
  **Off**. Hide it for On and for "?".
- Also check the worker's resolved `encoded` and refuse if it is set, as
  defence in depth. With the first rule in place the two never disagree.
- Never compute spoiler data (D), or write an export (C), for an encoded
  seed.
- The visualizer keeps refusing encoded ROMs, and W5 makes that deterministic.

### 4.2 The spoiler reveals other "?" outcomes

A map shows, for example, whether dungeon palettes or bosses were shuffled.
That is in the nature of a spoiler, but it is exactly what the page otherwise
hides. Section 5, question 2 asks how to handle it.

## 5. Questions for the owner

1. **Encoding "?"**: OK to offer the spoiler only when "Encode level data" is
   explicitly Off (section 4.1)?
2. **Other "?" outcomes**: a spoiler shows them. Show it behind a click with a
   one-line warning, or not at all when the flag string contains a "?"?
3. **Where the parser lives**: may ZORA vendor a pinned copy of the
   visualizer's core, with this repo as the source of truth? Or would you
   rather publish the core as its own small package?
4. **Licence**: the visualizer has none (all rights reserved by default,
   public repo). Before code moves into ZORA, should it get the same "all
   rights reserved, licence to be announced" notice, or a licence chosen now
   for both?
5. **Visualizer fixes**: go ahead with W1 and W3-W6 here? And for W2, a
   banner only, or full progressive labels from ZORA's byte at `0x07E50`?
6. **Hosted visualizer and testers**: should beta testers be pointed at
   streamlit.app at all, given that it uploads the generated ROM and the beta
   is confidential?
7. **Spoiler export (C)**: is one wanted for Archipelago or racers? If so,
   should its format be designed now, so that option D's JSON and the export
   are the same thing?

## Summary for the owner

- **The visualizer already reads unencoded ZORA ROMs well.** 200 of 200 seeds
  parse. Maps, caves, shop prices, Shop Items in the Item Pool, Randomize
  Letter, the `$0E` nothing code for empty rooms and Ganon's room,
  requirements and ZORA's hint texts are all right. Encoded ROMs are refused.
- **It gets these wrong:**
  - Randomize Magical Sword: a sword in a dungeon, a cellar, Armos or the
    coast shows as "No Item" in 95 of 100 seeds.
  - Progressive Items: shows the literal items.
  - Hint texts: 7 of ZORA's 45 are never read, and nothing shows who says
    which.
  - `cli.py` crashes on the recorder text.

  All are small fixes here, except "who says which hint", which needs ZORA's
  data.
- **The visualizer has no licence file.** Its code is all yours, so sharing
  it with ZORA is legally simple; the open question is what notice it
  carries.
- **Recommendation:**
  - Fix the misreads here now.
  - For ZORA's single-file beta, embed the visualizer's stdlib-only parser in
    ZORA's worker, behind a "Show spoiler" click, with a small SVG renderer
    on the page. It works offline, the ROM never leaves the page, there is
    one parser, and ZORA supplies the few facts the ROM cannot.
  - Skip URL handoffs.
  - Build a spoiler export file only if something else needs it.
- **Encoding stays safe if** the spoiler is offered only when the player set
  "Encode level data" to Off explicitly. Otherwise the button itself would
  reveal how a "?" resolved.
